# LAM latent action tour — local demo

A small Gradio app that lets you walk through the held-out transitions of
each of the 6 sweep checkpoints, watch the real `frame_t` / `frame_t+1`
pair, and (optionally) interpolate latent actions between two pinned
transitions.

## Run

Two steps. The cache step takes ~1 minute on the same GPU the sweep ran
on; the app step is instant after.

```bash
# 1) Precompute: encode 500 held-out transitions through every checkpoint
#    and save thumbnails. Outputs to runs/demo_cache/ (~22 MB).
python scripts/precompute_demo_cache.py \
    --ckpt_dir runs/sweep \
    --data_path /home/vai/data/ego100k_heldout \
    --n_transitions 500

# 2) Launch the app on http://127.0.0.1:7860
python demo/app.py
```

The cache directory is gitignored along with the rest of `runs/`, so you
need to re-run step 1 after cloning. Step 1 needs:

- the 6 sweep checkpoints under `runs/sweep/lam_*.pt` (regenerated by
  `python scaling.py …` per the top-level README), and
- a held-out video cache at `--data_path` (regenerated by
  `python scripts/cache_dataset.py --out … --n 50 --skip 2000`).

## What's in the UI

- **Branch + scale dropdown** swaps in any of the 6 trained LAMs.
- **Motion-percentile slider** is the main interaction. The 500 held-out
  transitions are sorted by `||f_t+1 - f_t||`; dragging from 0 → 100
  walks you from the most stationary worker frames to the most active.
  Both `frame_t` and `frame_t+1` update.
- **Scatter** is a 2D PCA of the latent action `z_eval` from this
  checkpoint, colored by motion magnitude. Click a point as a shortcut —
  the slider jumps to that transition's percentile rank.
- **Interpolation accordion (advanced)**: pin the current transition as
  A or B, then drag α from 0 → 1. We linearly interpolate `z` between A
  and B, run the FDM with A's `f_t` as anchor, and retrieve the nearest
  real `f_t+1` (no pixel decoder; we look up in held-out features).

## Why retrieval, not generation?

The LAM operates in DINOv2 feature space, not pixel space. We don't have
a feature → RGB decoder, so we can't *generate* novel frames. The
"retrieved frame" you see is the held-out clip whose `f_t+1` is closest
to the FDM's predicted feature vector. This is honest about what the
model knows and avoids reading meaning into hallucinations a generative
decoder would invent.

A pixel-space decoder is a Phase-2 deliverable per the proposal; until
then, retrieval is the right way to visualize what the model "thinks"
the next frame should look like.
